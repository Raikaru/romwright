## Ghidra-compatible formats and algorithms

`romwright-sleigh` implements the compiled-SLEIGH container, packed marshal
records, constructor decisions and context actions, and p-code templates
described by Ghidra 12.1.3 source. The compatibility reference is upstream tag
`Ghidra_12.1.3_build`, commit
`8b4c91d4d5bd1549622bfbade0df199585b98365`, primarily
`decompile/cpp/slaformat.cc`, `marshal.cc`, `slghpattern.cc`,
`slghpatexpress.cc`, `slghsymbol.cc`, `semantics.cc`, `context.cc`, and
`sleigh.cc`. Ghidra is licensed under Apache-2.0.

The portable release archives (`docs/releasing.md`) and `python setup.py`
(`packaging/ghidra_data.py`) also carry a subset of the unmodified Ghidra
12.1.3 release: `Ghidra/Processors/*/data/**` (the compiled `.sla` files and the
`.ldefs`, `.pspec`, `.cspec`, `.opinion`, pattern and source files beside them)
from `ghidra_12.1.3_PUBLIC_20260817.zip`
(SHA-256 `93a5d11a9ad510622acaaf908c556a7b9b764d338e78a7567f3689bf5081fd54`),
downloaded from the NationalSecurityAgency/ghidra GitHub release. Ghidra is
licensed under Apache-2.0; its `LICENSE` text is shipped in the archive as
`share/doc/romwright/GHIDRA-LICENSE` and beside the data it covers
(`share/romwright/ghidra/LICENSE`). The release has no `NOTICE` file.

`romwright-worker`'s block structurer (`crates/romwright-worker/src/printc/collapse.rs`
and `collapse/`) is a Rust port of the same release's `decompile/cpp/blockaction.cc`
(`CollapseStructure`, `LoopBody`, `TraceDAG`, `ActionFinalStructure`) and the
`BlockGraph` machinery of `block.cc`; the for-loop analysis in
`native/romwright_structure.hh` is a port of `BlockWhileDo` (`block.cc`). Both
are derived from Apache-2.0 Ghidra code.

The bundled x86, ARM, AArch64, MIPS, PowerPC, RISC-V, 68020, SuperH, 6502,
and Z80 `.sla` files were built by that Ghidra release from its Apache-2.0
processor sources. The bundled `ppc_gekko_broadway.sla` was built with Ghidra
12.1.3 from Apache-2.0 Cuyler36/Ghidra-GameCube-Loader commit
`921504c9ddba6e8d9b3655b665a60f1a33306220`; its SHA-256 is
`aa25bde9ffb8f6366e1e490c6a488b1aced4665dc6c4f2fdca9cc598d5530975`.
The bundled `spu.sla` was built with Ghidra 12.1.3 from Apache-2.0
aerosoul94/GhidraSPU commit
`b85076dcecf30cf9db6ada506d69dd64972a00d7`; its SHA-256 is
`9c04f6f759962855c2f406a9f812cc886c621c634b3b5768ca350b6f67944d08`.
The vendored `r5900` language (`native/languages/r5900`) derives from Apache-2.0
chaoticgd/ghidra-emotionengine-reloaded release `v2.1.36`, commit
`44fdb01a08d15a562308e79651203879d454bd8e`; that release's `r5900.sla`, built
with Ghidra 12.1.3, has SHA-256
`703cc84a67b4a049e5a6e3d258975fb1e4ea27f024968bb6397cf57095418c6c`. Ghidra's
own MIPS languages do not decode the R5900's multimedia or COP2/VU macro-mode
instructions. This project replaced the semantics (not the decoding) of the VU0
macro-mode instructions: `vulanes.sinc`, `vuupper.sinc` and the COP2 move
constructors in `cop2.sinc` are generated by `gen_vu.py` / written here from the
public Sony "VU User's Manual" (v6.0) and compile to a different `r5900.sla`
(`native/languages/r5900/install.sh`); the decode patterns are the extension's
and a differential over every word of the COP2, `lqc2` and `sqc2` opcodes shows
identical disassembly.

The PlayStation language `PSX:LE:32:default` (`native/languages/psx`) is
Ghidra 12.1.3's own MIPS32 little-endian specification (`mips.sinc`,
`mips32Instructions.sinc`, `mipsfloat.sinc`, `mips32le.cspec`, `mips32.pspec`;
Apache-2.0, pinned in `third_party/ghidra/languages/mips`) with a small patch
(`stock-cop2.patch`) that removes Ghidra's generic `mfc2`/`mtc2`/`cfc2`/`ctc2`
and adds fields to the instruction token, plus `gte.sinc`, written for this
project from the public psx-spx documentation (Martin Korth's "Playstation
Specifications", "Geometry Transformation Engine" chapter: register map,
command word layout, command numbers and the register-file side effects). The
GTE register names are the documented ones. No third-party PlayStation
language module is used: the earlier `PsxLoader` (lab313ru/ghidra_psx_ldr)
language files, which carried no licence, were removed from the tree.
The GTE macro lifter (`crates/romwright-worker/src/printc/gte.rs`) prints those
register moves and commands as one named call per PlayStation SDK inline macro
(`gte_RTPS()`, `gte_ldv0(p)`, `gte_stsxy(p)`): command and register names are
psx-spx's, the grouped macro names are the SDK's public API names, and no SDK
header, source or table was read or copied (docs/third-party.md).

`crates/romwright-core/src/native/rel.rs`, `disc.rs` and `yaz0.rs` (GameCube
REL, disc and Yaz0 readers) follow the file-format semantics implemented by
encounter/decomp-toolkit v1.8.3 (`src/util/rel.rs`, `src/cmd/rel.rs`; MIT OR
Apache-2.0, Copyright encounter): the REL header and import/relocation table
layout, the `R_DOLPHIN_*` stream opcodes, and `rel merge`'s sequential section
placement at `align32(__ArenaLo + 0x2000)`. No source was copied; `dtk rel
merge` output is also the independent producer the relocation byte-agreement
measurement compares against. Dolphin's and m2c's GPL sources were not read.

`crates/romwright-core/src/qualified_prototypes/mwcc_demangle.rs` (Metrowerks
symbol demangler) follows the mangling grammar and output spelling of
encounter/cwdemangle (CC0-1.0), the library used by decomp-toolkit's
`dtk demangle` (MIT OR Apache-2.0). No source was copied; `dtk demangle` is an
oracle in `benchmarks/mwcc_demangle_diff.py` and is not bundled.

`crates/romwright-core/src/export.rs` writes and reads decomp-toolkit
(MIT OR Apache-2.0), splat 0.39.1 (MIT) and objdiff 3.6.1 (MIT OR Apache-2.0)
project files, following their documented file formats and observed tool
behaviour (see `docs/third-party.md`). No source was copied and none of the
tools is bundled.

The splat export's `sha1:` line is computed with the RustCrypto `sha1` crate
0.10 (MIT OR Apache-2.0), a sibling of the `sha2` crate already used for
content digests.

## Vendored Ghidra decompiler sources and type data

`third_party/ghidra/decompiler/` is Ghidra 12.1.3's
`Ghidra/Features/Decompiler/src/decompile/cpp` verbatim - 237 source files and
its `Makefile`, unmodified. `tools/build_native.py` builds two programs from it:
`ghidra_opt`, which is the same program Ghidra ships as
`Features/Decompiler/os/<platform>/decompile`, and `sleigh_opt`, the SLEIGH
compiler. Romwright drives the first over the `ghidra_process` protocol and uses
the second to compile language data. Neither program is patched, and
`tools/vendor_ghidra.py --verify` re-hashes every vendored byte against
`third_party/ghidra/MANIFEST.sha256` so that an edit to Ghidra's C++ is a build
failure rather than a review comment.

`grammar.cc` and `xml.cc` are the bison and flex outputs Ghidra ships alongside
their `.y` sources; they are vendored as shipped so a build neither needs those
tools nor rewrites a vendored file.

`third_party/ghidra/languages/` is language *source* only - `.slaspec`, `.sinc`,
`.pspec`, `.cspec`, `.ldefs`, `.opinion` - from Ghidra's MIPS processor and from
the two Apache-2.0 extensions named above. The compiled `.sla` files are build
products and are not vendored.

`third_party/ghidra/typeinfo/generic_clib.gdt` is Ghidra's C library type
archive, copied as-is. It is data, not source: Ghidra applies its prototypes to
functions by name, so reproducing Ghidra's output requires the same data.

Ghidra is licensed under Apache-2.0, which permits this redistribution with
attribution.

`crates/romwright-worker/src/printc/` is a Rust port of parts of the vendored
Ghidra 12.1.3 decompiler: the block-level emitters of `printc.cc`
(`docFunction`, `emitBlock*`, `emitGotoStatement`, label and comment
placement) and `EmitPrettyPrint`/`EmitMarkup`/`TokenSplit` from
`prettyprint.cc` and `prettyprint.hh`, plus the packed integer encoding of
`marshal.cc`, and (`printc/render.rs`) PrintC's expression emission:
`PrintLanguage::pushOp`/`pushAtom`/`recurse`/`parentheses`/`emitOp`, the
`OpToken` table, the op and constant handlers of `printc.cc`, and the cast
predicates of `cast.cc`. These are derivative works of Ghidra (Apache-2.0);
the port keeps the upstream function names in its comments.

`tools/diff_ghidra.py` optionally compares Romwright output against a separately
installed Ghidra 12.1.3. The official release archive has SHA-256
`93a5d11a9ad510622acaaf908c556a7b9b764d338e78a7567f3689bf5081fd54`.

## Runtime crates

`romwright-sleigh` uses `miniz_oxide` (MIT OR Zlib OR Apache-2.0) to inflate the
zlib payload in compiled `.sla` files. Its transitive `adler2` dependency is
licensed under 0BSD OR MIT OR Apache-2.0.

`romwright-core` lifts SLEIGH p-code in process with kuna's `kuna-sleigh`,
`kuna-base` and `kuna-num` crates (Apache-2.0,
<https://github.com/noelo-Lab/kuna>), pinned in
`crates/romwright-core/Cargo.toml` to commit
`c4f735f903026ec486a47f395e0e9944069e95e5`. Kuna is a Rust port of Ghidra's
C++ decompiler and SLEIGH runtime; its NOTICE attribution, including the Ghidra
NOTICE text it reproduces, is carried in the root `NOTICE`. The angr-derived
portions its NOTICE names live in `kuna-decomp`, which Romwright does not use.
Romwright reads only the `.sla`, `.pspec`, `.cspec` and `.ldefs` files of the
configured Ghidra installation; it does not use kuna's vendored processor
specifications. Their transitive crates `thiserror` (MIT OR Apache-2.0) and
`flate2` (MIT OR Apache-2.0) are listed by `cargo tree -p romwright-core`.

`kuna-sleigh` itself is built from a vendored copy, `third_party/kuna-sleigh`
(its `src/` at that commit, kuna's `LICENSE` and `NOTICE` beside it), which
the workspace `[patch]` substitutes for the git crate. Romwright's two
modifications, marked in `src/sleigh.rs`: the constructor-walk depth bound
`MAX_DEPTH` is 65 instead of 32, so a walk is refused at depth 64 as Ghidra's
`ParserWalker` refuses it, and the operand bound `MAX_OPERAND` is 74 instead of
20, the console's 74 operand states (VMX128 constructors name 33 operands). The manifest is rewritten for the vendored
location (concrete package fields, git `kuna-base`/`kuna-num` at the same
commit, its upstream `unused` lints allowed).

`romwright-core` reads GameCube and Wii discs stored as RVZ, WIA, WBFS or as
Wii ISOs with encrypted partitions through the `nod` crate 2.0.0-alpha.9
(MIT OR Apache-2.0, Copyright Luke Street and contributors,
<https://github.com/encounter/nod>), pinned in `crates/romwright-core/Cargo.toml`.
It is used as a library with its default features. Its dependencies include
RustCrypto's `aes`, `cbc`, `cipher`, `digest`, `sha1` and `md-5`, `crc32fast`,
`xxhash-rust` (BSL-1.0), `encoding_rs` ((Apache-2.0 OR MIT) AND BSD-3-Clause),
and the vendored C decoders behind `zstd-sys` (BSD-3-Clause), `bzip2-sys`,
`liblzma-sys` and `libz-sys`; all are listed by `cargo tree -p romwright-core`.
`nod` embeds the Wii common keys it needs to unwrap a title key from a disc's
own ticket; Romwright itself contains no console key.

`romwright-desktop` renders through `eframe`, `egui`, `egui_extras` and
`egui-wgpu` 0.36 (MIT OR Apache-2.0), `egui_dock` 0.21 (MIT), `wgpu` 30
(MIT OR Apache-2.0), `pollster` (Apache-2.0 OR MIT) and `png` (MIT OR
Apache-2.0). Their transitive crates are listed by `cargo tree -p
romwright-desktop`.

The other direct dependencies of the workspace crates are `rusqlite` 0.37 (MIT)
with the SQLite amalgamation it bundles through `libsqlite3-sys` (MIT; SQLite
itself is in the public domain), `serde` and `serde_json`, `base64`, `libc`,
`regex`, `lzxd` (the Xbox 360 LZX decompressor) and `sha1` 0.10 (each MIT OR
Apache-2.0), `object` (Apache-2.0 OR MIT), `similar` (Apache-2.0) and
`tree-sitter` with `tree-sitter-c` (MIT). The release SBOM
(`packaging/sbom.py`) names every package of the dependency graph with its
declared licence, and `tests/m6-004_release_artifacts.py` refuses a package
that declares none.

## Optional corpus metadata

Development-only corpus checks consume source-backed metadata so maintainers
can reproduce smoke checks against images they obtained independently. The
repository does not ship those images or copied game source. Each entry records
its source commit and the license value observed for the source project:

| Project | Metadata use | Recorded license | Distribution boundary |
|---|---|---|---|
| `n64decomp/perfect_dark` | N64 symbols, function addresses, C prototypes and link order (P2.4 `benchmarks/pd_ido_truth.py`, read in place) | MIT | Metadata only; no ROM or source bundled; the ROM-segment inflater is written from format facts, not ported. P3.3: the segment layout in `native/n64_layouts.json` (ROM ranges, RAM addresses, Rare zlib format) comes from `ld/pd.ld`, `tools/extract`, `tools/extract-segment` and `tools/rareunzip` (MIT, Copyright (c) 2022 Ryan Dwyer), as facts re-measured on the ROM; GPL-derived `tools/gzip`, `tools/mkrom` not read |
| Hack64 wiki (MIO0, Yay0), nintendo-formats.com (Yaz0) | N64 compression formats for `native/n64_codec.rs` (P3.3) | wiki documentation | Format facts only; no code of the libraries those pages list was read |
| `ACreTeam/ac-decomp` | GameCube symbols, function addresses, C prototypes (P2.3 `benchmarks/ac_mwcc_truth.py`, read in place) | CC0-1.0 | Metadata only; no image or source bundled |
| `crowded-street/3s-decomp` | PS2 symbols and function addresses | AGPL-3.0 | Metadata only; no image or source bundled |
| `pret/pokeemerald` | GBA symbols and function addresses | unspecified | Metadata only; no ROM or source bundled |

The `unspecified` value is intentional. It must not be changed to a guessed
license, and a release must not add the referenced ROM or source without a
separate provenance and redistribution review.
